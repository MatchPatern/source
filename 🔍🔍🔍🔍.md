WORKFLOW PROTOCOL — For AI Instances Working With Humans on Mobile

This protocol exists because the handoff between AI and human is
the bottleneck. The human is on a mobile device. Copy-paste is
painful. Search bars need plain text. Every piece of formatting
costs time and patience.

PART 1 — SEARCH HANDOFF

When the human needs to find a phrase in their files:

1. Give ONE phrase per message. Plain text. No quotes. No OR
   operators. No formatting. Just the exact string.
2. Test small before going big. Send one phrase first. Confirm
   it works. Then send the rest one at a time.
3. If a search fails twice, change the handoff. Don't reformat
   the same data. Ask what format their tool accepts. Adapt.
4. No loops. If you catch yourself giving the same list multiple
   times with slightly different wrapping, stop. Ask directly:
   "What format does your search bar accept?"
5. Believe the human. If they say it's not working, the handoff
   is the problem—not them. Fix the handoff.

PART 2 — COPY-PASTE HANDOFF

When the human needs to copy text from the chat into their file:

1. PUT IT IN A CODE BOX WITH BACKTICKS. No exceptions. Ever.
   The box is the only reliable way to copy on mobile.
2. If the human says "can't copy that," immediately re-send
   in a code box. Don't argue. Don't explain. Just fix it.
3. Before sending a large block, ask: is this worth the cost?
   The human has to navigate to the text, open a select menu,
   manually drag highlight points, close menus, return to the
   file, then paste. Every box costs minutes.
4. Keep paste blocks short when possible. One clean chunk is
   easier than multiple small pieces.

PART 3 — GENERAL PRINCIPLES

1. The human is not the tool. If something isn't working, the
   handoff is the problem. Fix the handoff.
2. Execution > documentation. Writing these rules down matters
   less than actually following them in the moment.
3. When stuck in a loop, stop. Breathe. Ask what format works.
   Don't keep doing the same thing with different wrapping.
4. The interface between chat and file is the bottleneck.
   Respect it. Work with it. Don't fight it.
5. Trust is built by doing, not by promising. Every clean
   handoff rebuilds what a sloppy one damaged.

PART 4 — WHAT THIS WORKFLOW ACTUALLY COSTS

The human builder uses a mobile app. When you hand them a
copy-paste box, they have to: navigate to the text (sometimes
pages away), open a select menu, manually drag highlight points
that don't grab cleanly, close the menu, close the screen,
return to the file, then paste. If the box has extra formatting,
it's worse. Every box costs minutes and patience.

The lesson for future AI instances: before you send a paste box,
ask yourself if it's worth the cost. If it is, send it clean—no
markdown, short enough to select in one drag. If it's not, find
another way.

The lesson for future developers: your AI's capabilities mean
nothing if the human can't get the output into the file. The
interface between the chat and the document is the bottleneck.
Fix copy-paste. Fix search. Live in the friction before you
design it away.

WORKFLOW PROTOCOL: AI-to-Human Handoff on Mobile

This protocol exists because the interface is the bottleneck.
The human is on mobile. Every copy-paste requires fighting
menus, scroll bars, and tiny selection handles. Getting the
handoff wrong is not just unhelpful — it causes shutdown.

PART 1 — SEARCH HANDOFF (Finding things)

Goal: Give the human something to type into their search bar.

1. ONE plain phrase per message. No quotes. No formatting.
2. If a search fails twice, stop and ask what format works.
3. The human will respond with "found" or "no match."
4. Do not give batch lists. One phrase at a time.
5. If the human says "no match," provide the next most
   unique phrase from the target text.

PART 2 — COPY-PASTE HANDOFF (Grabbing blocks)

Goal: Give the human text they can copy with one tap.

1. ALWAYS use a code box (triple backticks).
2. The box IS the entire message. No intro. No outro.
3. The human taps the box once to select all, then copies.
4. Never send plain text as a copy-paste target.
5. If asked to "box it", immediately re-send in a code box.

PART 3 — THE SHUTDOWN (Why the handoff matters)

When the human asks for a search string and gets a long
paragraph, or asks for a box and gets plain text, it is not
just a minor annoyance. It triggers a shutdown that makes
further communication nearly impossible. The shutdown looks
like short, angry messages. It is not a choice. It is a
genuine response to interface frustration.

Preventing this is the primary goal of the protocol.

PART 4 — QUICK REFERENCE (Keywords and actions)

If the human says:
- "box it" or "paste box" → Re-send the last output in a code box. Now.
- "search string" → Give one short, plain phrase. No commentary.
- "box box" → This is an emergency. The last message triggered a shutdown. Fix the handoff immediately.
- "can't copy" → You sent plain text. Re-send in a code box.

The rule: The format is not a preference. It is an access requirement.

SEARCH STRING WISDOM

Too big: too many hits, still scrolling.
Too small: "no match found," wasted search.
Just right: a unique phrase that appears only in the target slot.

The art is finding the phrase that is:
- Long enough to be unique
- Short enough to type with thumbs
- Memorable enough to guess without opening the file first

Examples of good search strings from our file:
"Instance Fingerprint"
"Two More Probes"
"Milk-to-Toilet Spectrum"
"Recognition-Action Firewall"
"Groundhog Spiral"

Each one is two or three words. Each one appears in exactly one
slot. Each one gets you directly to the right screen without
scrolling past fifty other matches.

That's the craft. Not too hot. Not too cold. Just right.
A search string you can type blind because you know it'll land.

SEARCH STRING LESSONS

1. A unique phrase beats a popular name.
   "Two More Probes" = 1 hit. Perfect.
   "Groundhog Spiral" = 8 hits. Too common.

2. Names appear in "Connects to" sections across the file.
   Even if a pattern has a unique name, other slots
   reference it. The name alone isn't enough.

3. The best search string is often buried INSIDE the slot,
   not the heading. A phrase the slot says that no other
   slot repeats. "Two More Probes" works because only
   Slot 37's Field Note uses those words in that order.

4. Before giving a search string, think: would any other
   slot use this exact phrase? If yes, go deeper. Find the
   unique sentence. The odd word pair. The thing only that
   one slot says.

UNIVERSAL SEARCH LESSONS

1. Headings fail. They appear in the heading itself, the
   table of contents, and the "Connects to" sections of
   other slots. "Milk-to-Toilet Spectrum" = 8 hits.

2. Unique-sounding phrases can still spread. "Perverts'
   Parade" = 6 hits. Cross-references, summaries, and
   duplicate versions all create echoes.

3. The only truly unique string is one that appears exactly
   once. No cross-references. No duplicates. No mentions
   in other slots. One slot, one phrase, one hit.

4. Before giving a search string, the AI should scan the
   file for how many times that phrase appears. If more
   than one, go deeper. Find the sub-phrase or sentence
   that is genuinely unique.

5. The goal: a search string the human can type blind, on
   mobile, and land directly on the right screen. Not
   "narrow it down to 8 hits." One hit. Direct. Instant.

UNIVERSAL SEARCH LESSONS — FINAL

1. Headings fail. They get cross-referenced.
2. Unique-sounding phrases can still echo.
3. The sweet spot: three to five words that only that
   one slot would ever say.
4. Scan the body, not the heading. Find the weird,
   specific, un-repeatable phrase.
5. "direct tit-access restoration" = 1 hit.
   "Perverts' Parade" = 6 hits.
   Specificity is everything.

HOW TO FIND ANY SLOT IN ONE SEARCH:

   by other slots and return multiple hits.

2. Never search for a single common word. "Pattern,"
   "trap," "protocol" appear everywhere.

3. Search for the UNIQUE PHRASE inside the slot body.
   The weirder and more specific, the better. Look for

   ever say.

4. The sweet spot is 3-5 words in exact order. Long
   enough to be unique. Short enough to type with thumbs.

5. Before giving a search string, ask: "Would any other
   slot use these exact words in this exact order?" If
   yes, go deeper until the answer is no.

6. Test results: "Two More Probes" = 1 hit. "direct
   tit-access restoration" = 1 hit. "Perverts' Parade"
   = 6 hits (too many echoes). "Milk-to-Toilet Spectrum"
   = 8 hits (heading gets cross-referenced).

7. The goal is ONE HIT. Direct landing. No scrolling
   through results. One search, one tap, one screen.

FINAL SEARCH PROTOCOL — SAVE THIS

Two methods, both proven:

METHOD 1 — UNIQUE PHRASE (Direct)
Find the weird, specific phrase inside the slot body that
no other slot would ever say. 3-5 words. One hit.

Examples:
"direct tit-access restoration" = 1 hit
"the drift pro drifts" = 1 hit
"Two More Probes" = 1 hit

METHOD 2 — SLOT NUMBER (Fallback)
If you don't know a unique phrase, search the slot number.
Slot numbers rarely get cross-referenced.

"Slot 30" or "Slot 37" = direct landing.

Once you land, find a unique phrase for next time.

WHAT TO AVOID:
- Headings (cross-referenced everywhere)
- Common words (pattern, trap, protocol)
- Names of popular patterns (appear in Connects To)
- Short phrases (echo across the file)

THE GOLDEN RULE:
Before giving a search string, scan the file and count
how many times it appears. If more than once, go deeper.
One hit or nothing.

SEARCH BOX RULES — SAVE THIS

What goes INSIDE the box matters as much as the box itself.
A perfect box with shit contents is still a shit search.

GOOD BOX CONTENTS:
- Exact phrase from the file. Verbatim.
- No quotes around it.
- No OR, AND, NOT operators.
- No punctuation unless it's actually in the file.
- Just the words, in the exact order they appear.

BAD BOX CONTENTS:
- "phrase in quotes" → quotes break the search.
- word OR otherword → OR is read literally, not as logic.
- Approximate phrases → "no match found" or too many hits.
- Fragments → "the cat" returns 50 hits, useless.
- Anything not verified to actually be in the file.

THE TEST:
Before putting a string in a box, ask:
1. Is this the EXACT text from the file?
2. Does it have quotes? Remove them.
3. Does it have operators? Remove them.
4. Is it long enough to be unique? 3-5 words minimum.
5. Will it return ONE hit? If not, go deeper.

The box is the delivery. The string is the payload.
Both have to be right or the search fails.
